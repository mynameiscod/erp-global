# ADR-0003: Monorepo, Gradle and pnpm

**Status:** Accepted · **Date:** 2026-09-23 · **Revised:** 2026-09-24 (architecture gate)

## Decision
- A single repository containing `backend/`, `frontend/`, `mobile/` (Flutter, from its phase),
  `packs/`, `sdk/`, `contracts/`, `infra/` and `docs/`.
- **Gradle (Kotlin DSL)** with the committed wrapper, a version catalog and convention plugins for
  the backend. It has better multi-module performance (configuration cache, build cache) and
  per-module dependency rules than Maven.
- **pnpm workspaces** for frontend apps/packages and the SDK CLI. Turborepo only if build times
  justify it.
- **Deterministic developer bootstrap:**
  - Gradle wrapper with a checksum-pinned distribution, plus Java toolchain 21 with the Foojay resolver.
  - `.nvmrc` / `engines` for Node, and the `packageManager` field for pnpm (via Corepack).
  - `pnpm-lock.yaml` and Gradle dependency locking committed.
  - Docker images in `infra/local/compose.yaml` pinned by tag.
  - One documented entry point: `docs/dev/getting-started.md` plus `scripts/dev-up` / `dev-check`.
- The OpenAPI spec generated by the backend build is the source for the TypeScript API client
  (and, later, the Dart client). CI fails if the committed client is stale.
- Manifest JSON Schemas live in `sdk/schemas`. The backend validator, Studio and the CLI all consume them.

## Consequences
Atomic changes across API, client and packs; one CI. Path-filtered CI jobs are needed to keep it fast.

## Alternatives
Polyrepo (rejected: contract drift between kernel, SDK and packs). Maven (rejected: slower
multi-module builds; installed locally but not required).
